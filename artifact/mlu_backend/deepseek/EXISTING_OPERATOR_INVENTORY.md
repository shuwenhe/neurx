# Cambricon MLU590-M9 existing operator inventory

## Executive summary

The production container on `tza-0a09-ai01-em9` has a deployed MLU software stack and compiled extensions for GEMM, grouped GEMM, RMSNorm, Flash Attention, MLA transforms, RoPE, KV cache and MoE. Its editable vLLM-MLU checkout registers DeepSeek V2 and contains the corresponding dispatch paths. The active eight-card workload is GLM, and CNMON confirms device contexts and memory usage. No captured kernel trace or operator-level acceptance record establishes which kernels ran, their accuracy, or their performance. DeepSeek-V2-Lite execution remains unverified.

NeurX has compiled MLU availability diagnostics and a CPU-validated GEMM reference. Its Device ABI plugin lacks a native operator launch path. The production container's Ubuntu 24.04 SDK is useful as compatibility evidence for an isolated userspace. The Ubuntu 20.04 host has CNDev and a toolkit archive package, with no usable native CNRT/CNNL installation found. All eight cards were occupied in the allocation audit. This investigation used read-only package and source inspection and started no MLU workload.

## DeepSeek execution trace in the production checkout

1. Editable package entry points use plugin groups `vllm.platform_plugins` and `vllm.general_plugins` to call `V/__init__.py:register_mlu_platform` and `register_mlu_hijack`. `V/model_executor/models/__init__.py:77` maps the checkpoint's `DeepseekV2ForCausalLM` architecture to `V/model_executor/models/deepseek_v2.py:MLUDeepseekV2ForCausalLM`.
2. **GEMM.** The model projections invoke vLLM linear modules. `V/model_executor/layers/linear.py:50` replaces unquantized linear apply and calls `mlu_ops.matmul` at line 74. `V/_mlu_ops.py:1296` delegates to TMO, whose `T/_ops.py:2290` wrapper selects `torch.ops.torch_mlu_ops.matmul` or a variant. The installed CNNL also exposes `cnnlMatMul_v2`. The wrapper and header alone do not establish that every TMO GEMM uses that CNNL symbol.
3. **RMSNorm.** `V/model_executor/layers/layernorm.py:144` supplies the out-of-tree dispatch. It calls `V/_mlu_ops.py:84`, then `T/_ops.py:323`, which selects `fused_layernorm_alloc` or `fused_layernorm` with residual handling. This is a compiled extension route. The exact CNNL or custom kernel underneath remains unverified.
4. **Attention.** `V/platforms/mlu.py:80` selects `TMOFlashMLABackend` for an MLA path. The model's fused decode branches call `fused_mla_q` and `fused_mla_kv` at `deepseek_v2.py:393,433`. `V/v1/attention/backends/mla/tmo_flashmla.py:767,804,850` calls cached-query attention or Flash Attention with cache handling. `V/model_executor/layers/attention/mla_attention.py:374` also routes through the vLLM unified-attention custom op where configured. Q/KV transforms and cached attention are separate operations.
5. **Framework paths.** The reference MoE implementation moves token counts to CPU/NumPy and loops over experts. The vLLM-MLU checkout also contains tensor alternatives in `native_moe.py`. Their presence does not show CPU fallback in production. TMO, torch_mlu, CNRT/CNDrv and vendor libraries are present in the container. A kernel trace or exact native implementation is required to assign a particular wrapper call to CNNL versus a custom kernel and to establish execution on the MLU590-M9.

The public Cambricon repository is upstream context. The deployed checkout and its metadata provide the paths and versions above. [Cambricon vLLM-MLU upstream](https://github.com/Cambricon/vllm-mlu)

Source is `/app/shuwen/model/DeepSeek-V2-Lite/config.json`, `modeling_deepseek.py` and the local safetensors headers. Three shards were present at inspection, containing 4,311 BF16 entries in total. The index expects 980 entries in missing shard 4. Tensor data checksums were outside this header audit. The config has no weight quantization configuration.

Flash Attention, paged or latent-compressed cache, fused Add+RMSNorm, fused SiLU-and-multiply, and grouped GEMM are optimization choices. FP16 conversion and INT8/INT4 quantization are separate deployment choices. LayerNorm, GELU and ReLU are outside this model's forward path. ArgMax is an optional greedy decoding policy. AllReduce and expert all-to-all depend on the chosen parallel deployment. Single-card inference can validate model semantics without them.

## Development priorities

1. **Native BF16/FP16 GEMM and runtime gate.** Projections and expert layers depend on this. NeurX has a CPU reference and diagnostic stub. Medium engineering difficulty after a reserved MLU and approved SDK are available. Verify CNRT transfers and cleanup, then compare kernel output with the independent FP32 oracle on packed, rectangular and padded shapes. Include the 2048-to-3072 and 2048-to-1408 projections. Separate device latency, transfer latency, TFLOPS and workspace bytes. Reuse vendor GEMM first and select optimizations from measured results.
2. **MLA, YaRN and cache correctness.** The 512-wide KV latent and split rotary dimensions are specific to this architecture. Existing vLLM dispatch provides a reference implementation path. NeurX lacks tested device kernels and stateful cache integration. High difficulty. After GEMM, compare layer intermediates, full-prefill versus cached decode logits, masks and position scaling. Measure prefill tokens/s, per-token decode latency and cache bytes versus context length.
3. **MoE routing and grouped experts.** Six of 64 experts per token create irregular small GEMMs, and the reference host-side token-count handling introduces synchronization. Medium to high difficulty. Build on the accepted GEMM and activation path. Compare FP32 router scores, selected experts, weighted combine and expert output, including ties, empty experts and skewed loads. Measure routing, dispatch, group GEMM and combine separately across token counts and imbalance. Keep multi-card collectives outside initial single-card acceptance.

**Monday technical assessment:** Use BF16/FP16 GEMM with a non-square projection and an independent FP32 oracle. Present the existing CPU validation and the exact device acceptance protocol. Report MLU numerical or timing results only after the compatible runtime and reserved card gates pass. An isolated RMSNorm test is a useful follow-up once transfers work.

## Verification limits

Implemented source and installed binaries were inspected. The previous CPU reference and ABI results were reviewed. No new source build, GPU workload, benchmark, container mutation, driver change or package installation was performed. Operator-level hardware execution, correctness and performance on this machine remain unverified for the inventory rows. The live production container is concrete evidence that the host driver and an isolated newer MLU userspace coexist, while NeurX still needs an approved image, device allocation and runtime acceptance.
